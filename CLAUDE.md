# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A desktop ERP for a medical aesthetics distributor (Turkish UI throughout — do not translate strings to English), branded **Elffarma Paket Programı**. Despite the package name (`klinik-yonetim`) and the original MVP scope, this has grown far past "clinic management": it now covers doctors/customers (with billing info, Şahıs/Hastane type, payment due dates), stock (categories, barcode, expiry, critical-stock alerts, a movement ledger, daily stock counts), tahsilat (payments) with invoice attachments, congresses/workshops (participants, per-doctor product distribution, package pricing, remaining-stock tracking), general sales & returns, a sales-rep panel, doctor visit logs, expenses, a yearly budget-vs-actual module, reminders + a real calendar (FullCalendar-based Ajanda), Excel/Word/PDF export everywhere, and a fully theme-able UI (9 brand colors + a black/gold default, 3 icon sets, light/dark mode). Multiple staff accounts share one Supabase-backed database (admin vs staff roles).

As of 2026-07-26 (v1.0.0 in `CHANGELOG.md`) this is treated as **the live production codebase** — new work is additive on top of it, not a rewrite. Three docs, in order of authority for "what currently exists":
1. **`CHANGELOG.md`** — chronological record of what each module actually does and when it shipped. Read this first to understand current scope.
2. **`DESIGN_SYSTEM.md`** — the canonical UI/UX reference (layout skeleton, nav order, component variants, theme system, icon sets, export mechanism). When adding a screen, follow this document, not intuition.
3. This file (`CLAUDE.md`) — architecture/data-layer conventions that don't belong in either of the above.

An older phased build plan lives at `/Users/erkankongul/.claude/plans/swift-beaming-mochi.md` — it describes the *original* MVP (customers/stock/payments/appointments only) and is kept for historical "why" context, but it does **not** reflect the current module set; don't use it to infer what exists today.

## Git workflow (auto-commit, no confirmation needed)

Per explicit user instruction (2026-07-29): after finishing each change (a completed task/feature/fix, not every intermediate edit), automatically — without asking for confirmation first —
1. bump the patch version in `package.json` (`1.5.0` → `1.5.1` → ...),
2. add a short 1-2 line entry to `CHANGELOG.md` under a new `## [x.y.z] - <date>` heading describing what changed,
3. `git add`, commit (Turkish message, same style as existing history — short, describes the "why"/what changed), and
4. `git push origin main`.

This overrides the general "never commit without being asked" default for this repo specifically. Still use judgment on *grouping*: a multi-step task discussed across several conversation turns that forms one logical change should land as one commit/version bump when the task is done, not one per file edit.

## Architecture

**Electron + Vite + React + TypeScript**, single renderer window, no separate backend server — the renderer talks directly to Supabase (Postgres + Auth + RLS + Storage) using the anon key. `vite-plugin-electron/simple` builds `electron/main.ts` and `electron/preload.ts` alongside the renderer from one `vite.config.ts`.

**Security boundary**: the renderer has `nodeIntegration: false` / `contextIsolation: true`. It never gets direct Node/Electron access — `electron/preload.ts` exposes a narrow set of methods on `window.electronAPI` (`openWhatsApp`, `notify`, `onDeepLinkRecovery`, `googleDriveUpload`, `googleDriveTestConnection`) via `contextBridge`, typed in `src/types/global.d.ts`. `electron/main.ts` validates that `openWhatsApp` URLs match `^https://wa.me/` before calling `shell.openExternal`; `onDeepLinkRecovery` feeds the `elffarmapaket://reset#access_token=...` password-reset deep link (registered as the app's default protocol handler) into the renderer via IPC so React Router's own hash routing isn't disturbed. `googleDriveUpload`/`googleDriveTestConnection` (bkz. `electron/googleDrive.ts`) exist because Google's service-account JWT-Bearer token flow and the Drive API are not CORS-enabled for browser-context callers — the renderer (a real Chromium context under contextIsolation) gets a hard "Failed to fetch" calling them directly, so the JWT signing (Node's `crypto`, not Web Crypto) and the actual HTTP calls run in the main process instead, with only the already-fetched service-account JSON and results crossing the IPC boundary. Do not widen this bridge without keeping the `wa.me` validation. `electron/main.ts` also runs `electron-updater`'s `autoUpdater.checkForUpdatesAndNotify()` on startup, but only when `app.isPackaged` — never in `npm run dev`, since there's no update feed to check against there.

**Data layer / authorization model**: all access control is enforced in Postgres via Row Level Security, defined in `supabase/schema.sql` — this file is the single source of truth for the *entire* schema (22 tables as of this writing) and is meant to be pasted whole into the Supabase SQL editor (idempotent: uses `create table if not exists`, `add column if not exists`, `drop policy if exists` + recreate, etc.), not run via migrations tooling. The other `supabase/*.sql` files are the historical incremental patches that `schema.sql` was assembled from — keep them for the audit trail, but treat `schema.sql` alone as authoritative and always fold new schema changes back into it rather than dropping another one-off file next to it. Key points a change here must preserve:
- `public.staff` mirrors `auth.users` 1:1 (same `id`). A trigger (`handle_new_user`) auto-inserts a `staff` row on signup — the *first* user ever created becomes `role='admin'` automatically, everyone after that defaults to `role='staff'`; admins reassign roles from the app afterward. There is no separate "create staff" admin UI flow that calls `auth.admin.createUser` — new staff accounts are created directly in the Supabase dashboard.
- `is_admin()` / `is_active_staff()` are `SECURITY DEFINER` SQL functions used inside RLS policies to check the caller's role without recursive-RLS issues; reuse them for any new table's policies rather than inlining subqueries.
- `products.current_quantity` is a denormalized cache. It must only be mutated through the `record_stock_movement(...)` RPC (also `SECURITY DEFINER`), which inserts the audit-trail row into `stock_movements` and updates the cached quantity atomically. Never `update products set current_quantity = ...` directly from the client. `sales` (general sales/returns) and congress product distribution both trigger this RPC rather than writing stock some other way.
- Shared-trust model (any active staff member can read/write all rows, no per-staff siloing) applies to almost everything: `customers`, `stock_movements`, `payments`, `appointments`, `congresses` + its child tables, `doctor_visits`, `sales`, `sales_reps`, `expenses`, `budget_targets`, `invoices`, `reminders`, `stock_counts`/`stock_count_items`, `customer_pending_products`. Admin-write / staff-read applies to `staff`, `products`, `whatsapp_templates`, `app_settings`. The `invoices` storage bucket (payment/invoice file attachments) is private and gated on `auth.uid() is not null` rather than `is_active_staff()`.

**Frontend structure**:
- `src/lib/auth.tsx` — `AuthProvider`/`useAuth()`. Wraps Supabase session state and loads the matching `staff` profile row (role, active flag) on sign-in; this is what `AppShell` and route guards key off of, not the raw Supabase session.
- `src/lib/supabaseClient.ts` — the one Supabase client instance; also exports `CLINIC_NAME` (from `VITE_CLINIC_NAME`) and the "remember me" storage-mode logic (localStorage vs sessionStorage session persistence).
- `src/features/<name>/` — one folder per domain module, each following the same `api.ts` (raw Supabase calls) + `hooks.ts` (TanStack Query wrappers — mutations show `sonner` toasts on success/error and invalidate the relevant query key) + components shape: `whatsapp`, `customers`, `stock`, `stockCounts`, `payments`, `expenses`, `budget`, `congresses`, `doctorVisits`, `sales`, `salesReps`, `invoices`, `reminders`, `staff`, `appSettings`, `alerts`, `exchangeRates`, `offline`. When adding a new domain, mirror the shape of the closest existing feature rather than inventing a new one.
- `src/features/whatsapp/normalizePhone.ts` and `renderTemplate.ts` are the load-bearing WhatsApp utilities: phone numbers are canonicalized to `+90XXXXXXXXXX` before being turned into `https://wa.me/<digits>?text=<encoded message>` links; `openWhatsApp()` calls `window.electronAPI.openWhatsApp` (falls back to `window.open` when running outside Electron, e.g. `vite preview`). `WhatsAppSendDialog.tsx` is the reusable "pick a template → preview → send" dialog, with an optional "mark as sent" checkbox (there's no way to detect an actual send through `wa.me`, so this is a manual, honesty-preserving toggle).
- `src/features/offline/useOfflineSync.ts` + `src/lib/offlineQueue.ts` + `src/lib/offlineMutation.ts` — a real offline write queue (see "Offline behavior" below).
- `src/features/alerts/useAlertsSummary.ts` — the single place that aggregates critical-stock, expiry, payment-due, missing-balance/product, and upcoming-congress warnings; both the TopBar notification bell and `RemindersPage.tsx` read from this one hook. Add new alert types here, not in the pages that display them.
- `src/features/appSettings/` — `app_settings` key/value table wrapper: brand theme (`brandThemes.ts`, `useApplyBrandTheme.ts`), icon set (`iconSets.ts`), and color mode (`useColorMode.ts`, toggles the `.dark` class on `<html>`).
- `src/features/ai/` — the AI infrastructure (provider-agnostic, deliberately self-contained — nothing outside this folder imports a provider class directly). `AIService` (`AIService.ts`) is the single entry point every AI call must go through; it wraps whichever `AIProvider` is active (`OllamaProvider` | `OpenAIProvider` | `GeminiProvider` | `ClaudeProvider`, `providers/createProvider.ts` is the factory) and logs every call to `ai_usage_logs`. Ollama/OpenAI/Gemini all speak the OpenAI-compatible `/chat/completions` + `/models` contract via the shared `providers/openaiCompatible.ts` client; Claude talks Anthropic's native Messages API internally but exposes the identical `AIProvider` interface. Default provider is Ollama (local, no API key) with model `qwen2.5:3b` (downgraded from `qwen2.5:7b` — the 7b model froze low-RAM machines and occasionally leaked Chinese tokens into Turkish output) — provider/baseUrl/model are user-configurable from Settings > Yapay Zekâ (stored in `app_settings` under key `ai_settings`, same pattern as brand theme/icon set). Cloud-provider API keys have two sources, resolved in `useAIService.ts`/`AIProviderSettings.tsx` with personal-over-shared precedence: (1) a per-staff-member key in `public.staff_ai_keys` (`staff_id` PK referencing `staff(id)`, one column per provider — `openai_api_key`/`gemini_api_key`/`anthropic_api_key`) entered from the "Kendi API Anahtarım" field in Settings > Yapay Zekâ, gated by row-level RLS policies scoped to `staff_id = auth.uid()` (a deliberate departure from this app's usual shared-trust `is_active_staff()` pattern, since this table holds secrets — never reuse the shared-trust pattern for it); falling back to (2) `.env` (`VITE_OPENAI_API_KEY` / `VITE_GEMINI_API_KEY` / `VITE_ANTHROPIC_API_KEY`), baked in at package time for a shared/organization-wide key if one is ever accepted. Neither path writes a cloud API key into the shared `app_settings` table. Conversation history lives in `ai_conversations`/`ai_messages` (shared-trust RLS, same as most tables). `useAIStartupCheck()` (wired into `AppShell`) pings the active provider once per app session and toasts a warning if unreachable or the model isn't pulled yet — non-blocking. As of this writing only a minimal test chat panel (Settings page) exercises the pipeline end-to-end; concrete AI features (smart search, natural-language queries, etc.) are future work built on top of `AIService`, not yet implemented.
- `src/components/ui/` — hand-written shadcn/ui-style primitives (not generated via the shadcn CLI) built on Radix primitives + `class-variance-authority`. The current visual language ("premium ERP", glassmorphism + black/gold default theme) is documented in full in `DESIGN_SYSTEM.md` — that document, not this one, is the reference for anything color/component/layout related. Use `cn()` from `src/lib/utils.ts` for class merging in any new component.
- `src/components/layout/AppShell.tsx` — the persistent sidebar-nav shell + TopBar (search box, connection indicator, notification bell, profile menu) plus an online/offline indicator (`src/hooks/useOnlineStatus.ts`). The nav order lives in its `navItems` array — check that array directly rather than assuming; per `DESIGN_SYSTEM.md` new modules get appended to the end, existing order doesn't get reshuffled. `ComingSoonPage.tsx` was the placeholder for draft nav entries before they became real modules — as of now every nav entry is a real module, so this component is unused; it's kept only as the pattern to reuse if a genuinely draft page is added again.
- `src/i18n/tr.ts` — centralized lookup tables for enum-like display strings (nav labels, appointment/stock-movement/payment-method/staff-role display values). Most other UI copy is written directly as Turkish JSX text rather than routed through an i18n layer (no localization abstraction — this is a single-language Turkish app by design).
- `src/types/database.ts` — hand-maintained TypeScript interfaces mirroring `supabase/schema.sql` (no generated types / Supabase CLI codegen in use). Keep these two files in sync manually when the schema changes; this file has historically lagged `schema.sql` (it was missing several tables as of the 2026-07-28 schema consolidation) — verify it against `schema.sql` before assuming it's complete.
- `src/lib/exportData.ts` + `src/components/ExportMenu.tsx` — the shared Excel/Word/PDF export mechanism used by every list page (PDF uses an embedded Noto Sans font, `src/lib/notoSansBase64.ts`, for Turkish characters). Don't build a page-specific export path; reuse this.

**Path alias**: `@/*` → `src/*`, configured in both `tsconfig.app.json`/`tsconfig.json` and `vite.config.ts`'s `resolve.alias` — keep both in sync if it ever changes.

**Offline behavior**: there **is** a real offline write queue — this used to be out of scope but no longer is. `src/lib/offlineMutation.ts` exports `offlineInsert`/`offlineUpdate`/`offlineUpsert`/`offlineDelete`/`offlineRpc`; most feature `api.ts` files call these instead of `supabase.from(...)` directly. When online, they write straight through to Supabase; when offline (or a write fails with a network error), the mutation is queued via `src/lib/offlineQueue.ts` and an optimistic result is returned so the UI/calling code doesn't need special-case handling. `useOfflineSync()` (`src/features/offline/useOfflineSync.ts`) drains the queue in order as soon as `navigator.onLine` fires, stopping (not skipping) on the first failure so later mutations that might depend on an earlier one never get applied out of order. `useOnlineStatus` still only drives the visual connection indicator on top of this — it isn't the mechanism that decides whether a write queues. When adding a new feature's `api.ts`, follow the existing pattern (see `src/features/stock/api.ts` or `src/features/sales/api.ts`) rather than writing directly against `supabase.from(...)`.
